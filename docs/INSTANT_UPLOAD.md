# 秒传（Instant Upload）判定原理

本文说明「秒传」到底是什么，以及本项目如何可靠地判定它。
参考资料：

- [CloudDrive2 核心功能](https://www.clouddrive2.com/features.html)（官方）
- [如何实现文件秒传（掘金）](https://juejin.cn/post/7321049399282827274)

---

## 一、秒传是什么

**不是「传得快」，而是「根本没传」。**

一般上传流程是：客户端把文件数据一个字节一个字节发到服务器。

秒传的流程完全不同：

```text
客户端：算出文件的哈希值（MD5 / SHA-1）
   ↓
客户端：把「哈希 + 文件大小」发给服务器，先问一句
   ↓
服务器：在自己的存储里查，这个哈希是否存在？
   ├─ 不存在（notHash）  → 正常上传，把文件数据传上去
   ├─ 已存在（hasHash）  → **不接收任何数据**，直接建一条记录指向已有文件 ← 这就是秒传
   └─ 正在被别人传（hashIng） → 等对方传完，然后同样直接建记录
```

关键点：**115 上任何一个账号里存在相同哈希的文件，你上传时都能命中秒传**。
所以即使是自己第一次传这个文件，也可能是秒传。

CloudDrive2 官方文档对此的表述：

> CloudDrive2 的做法是尽最大可能利用云盘的秒传机制。秒传的原理是：
> 上传前先算出文件的哈希值发给服务器，服务器发现这个文件已经存在，
> **就不再接收文件数据**，而是直接建一条新的文件记录指向已有的数据。

## 二、怎样才能判定出秒传

### 错误的判据：看耗时

「耗时小于 N 秒就算秒传」这个思路不可靠，因为耗时受很多因素影响：

| 干扰因素 | 后果 |
|---|---|
| CD2 并发上限造成排队 | 秒传任务排队 20 分钟后才完成 → 被误判成非秒传 |
| 网络快、文件小 | 真实上传 2 秒传完 → 被误判成秒传 |
| 预处理/算哈希耗时 | 大文件算哈希本身要几十秒 → 被误判成非秒传 |

本项目最初就是用耗时判定的，结果导致**秒传记录几乎为空**、
同时**大量任务被误判超时**（排队时间被算进去了）。

### 正确的判据：看有没有真的传数据

秒传的定义就决定了它的可靠特征：

> **完成时实际传输的字节数 ≈ 0**

对应到 CD2 的 `UploadFileInfo`，就是字段：

```protobuf
uint64 size = 3;              // 文件总大小
uint64 transferedBytes = 4;   // 实际已传输字节数（注意官方拼写只有一个 r）
```

判定规则：

```python
if size > 0 and transfered_bytes / size < 0.01:
    # 传输量不到 1%，说明数据从没真正传过 → 秒传
```

留 1% 的容差是为了兼容 CD2 在预处理阶段可能统计到的少量内部读取。

### 补充：秒传可能「快到看不见」

秒传往往在两次轮询之间（默认 3 秒）就完成并从列表中消失了。
所以除了观测到 `Finish` 状态，还必须处理**任务直接消失**的情况：

```text
任务消失 + 消失前 transferedBytes/size < 1% + 不是失败状态
   → 判定为秒传完成
```

本项目在 `_handle_task_vanished()` 里实现了这条兜底。

## 三、115 的一个额外旁证

115 网盘对上传有限制（来自 CloudNAS 公告）：

> 115网盘上传**非秒传**文件最大 5GB（后调整为 20GB），
> **不支持断点续传和多线程上传**；**秒传的文件不受此限制**。

这说明 115 侧确实把秒传和普通上传当作两条完全不同的路径处理，
与我们「不接收数据」的判断一致。

## 四、本项目怎么用

### 判定发生在两处

| 场景 | 处理位置 |
|---|---|
| 观测到 `Status == Finish` | `_record_instant_upload()` |
| 任务从列表消失 | `_handle_task_vanished()` |

两处都调用同一个判定逻辑，保证口径一致。

### 界面上能看到证据

「任务监控 → 秒传详情」有一列 **实际传输**：

- `0（未传数据）` —— 真秒传，绿色高亮
- 其他数值 —— 实际传了数据，不该出现在这里（说明判定有偏差，需要反馈）

保留这一列的意义是**让判定可被验证**，而不是让用户盲信统计数字。

### 相关配置的影响

- **规则阈值**（`timeout_threshold`）现在**只用于超时拦截**，
  不再参与秒传判定。
- 只有命中规则的任务才会被记录（作用域过滤），未命中规则的任务完全不入库。

## 五、常见疑问

**Q：为什么我的任务耗时很短，却没被记录成秒传？**
检查「实际传输」列。如果显示传了几百 MB，那说明 115 上没有这个文件，
走的是真实上传 —— 只是网速快。这属于正常情况。

**Q：115 上明明有同一个文件，为什么还是真实上传？**
可能原因：
1. 文件被改动过（哪怕 1 个字节，哈希就完全不同）；
2. 视频文件的元数据（如 MKV 的标题、字幕轨）不同，导致整体哈希不同；
3. 115 的哈希索引尚未建立（刚上传的文件可能需要时间）。

**Q：秒传记录为空，但任务列表里有已完成的？**
确认那些任务是否命中了规则。未命中规则的任务按设计不会被记录。
